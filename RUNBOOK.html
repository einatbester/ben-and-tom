Why this exists

The goal

This is not a real product — it's a sandbox for learning how to manually control a live website end to end: push code, host it publicly, attach a real (free) custom domain, and later update the live site with confidence. The real motivation is a separate, real project: frooteria-local-shine, a redesign built for Frooteria Juices & Bagels (Munich), currently live at frooteria.de. Before ever touching that real, live domain, this project is where the mistakes get made safely.

Operating it

How to run it

Run locally
npx http-server ./ from the project root — serves on http://127.0.0.1:8081
Ship a change
git add the edited files, commit, git push to main — GitHub Pages rebuilds automatically within about a minute

The site is plain index.html + style.css — no build step, no framework, no dependencies. That's intentional: the point of this project is the deployment/domain mechanics, not the site itself.

Output

A live, public website at https://einatbester.github.io/ben-and-tom/ (confirmed working, HTTP 200). Once the is-a.dev pull request below is merged and the custom domain is attached, the same site will also answer at https://besterbros.is-a.dev.

Under the hood

How it works

Hosting
GitHub Pages, source set to the main branch, root folder. Serves index.html/style.css directly, no build step.
DNS layer
A besterbros.json file submitted to is-a-dev/register declares a CNAME record: besterbros.is-a.dev → einatbester.github.io.
Platform layer
Once the PR merges, ben-and-tom's repo Settings → Pages → Custom domain must also be set to besterbros.is-a.dev. This writes a CNAME file into the repo and is what actually claims the domain for this specific repo (not any other repo on the same account).

Why it matters: the DNS record alone is not enough — until the Platform layer step is done too, besterbros.is-a.dev will resolve to GitHub's servers but show is-a.dev's generic "not registered" page, not this site.

Why we chose this

Key decisions

is-a.dev vs Netlify/Vercel
Chose to do this manually with GitHub Pages + is-a.dev instead of Netlify/Vercel specifically because those platforms automate away the DNS/custom-domain steps — the whole point of this project is to feel every step of that process by hand, since the same steps (minus the free-domain part) are what a real switch on frooteria.de will require.
is-a.dev vs a real paid domain
Chose is-a.dev because it's free and it does exercise the real mechanic — a domain pointing somewhere via a DNS record that you change and wait to propagate. Good practice, but not a perfect analogy: is-a.dev's registration flow is a slow, human-reviewed GitHub pull request, while the real frooteria.de switch will happen instantly and self-service inside a registrar's DNS dashboard (see below) — nobody has to approve it. More importantly, is-a.dev subdomains carry no email, so this practice never surfaces the single biggest real risk of a domain switch: silently breaking a business's email by repointing DNS carelessly. That risk is real for frooteria.de and invisible here.
frooteria-local-shine kept private
The real estate redesign repo is a private GitHub repo on purpose, so the prototype isn't publicly visible under the real business's name before it's ready to show the client — normal, legitimate practice, not an issue, as long as it's never presented publicly as their live site without consent.
Real-world context

How frooteria.de works today

Registrar / DNS
GoDaddy (ns81.domaincontrol.com, ns82.domaincontrol.com) — both the domain registration and its DNS records live here, self-service via GoDaddy's dashboard
Hosting
81.169.202.53 — a German shared-hosting IP range (Strato), not GitHub Pages or any platform used in this practice project
Email
The MX record points at www.frooteria.de itself — their email is very likely running on the same server as their current website

Why it matters: because email and the website share infrastructure here, the real cutover cannot just be "point the domain at the new host" — it has to specifically avoid touching nameservers or the MX record, or their email goes down silently along with the old site. See the switch-safety checklist in Field Notes — that work hasn't started yet.

Field notes

Only matters again if…

Everything below is already handled — nothing here needs action right now.

…the is-a.dev pull request (#52219 on is-a-dev/register) still shows as open/pending next time you look. That's expected — it's a volunteer-reviewed queue with no fixed turnaround. Check its status before doing anything else with the domain; don't resubmit unless it was explicitly closed/denied again.

…the PR gets denied again for an incomplete template. The template uses hidden HTML comment markers (e.g. <!-- WEBSITE_PREVIEW_START -->) that GitHub's rendered editor can silently mangle. Always edit on the "Write" tab and paste the full template back in, rather than typing inside the rendered preview.

…you ever need to demo frooteria-local-shine publicly before it's finished. Its repo is private on purpose, so it has no live Pages link at all right now. Either flip it public temporarily for the demo, or share via a local tunnel — don't leave it public by default.

Before the real cutover

Frooteria.de switch-safety checklist

The real switch hasn't happened yet — none of this is done. Work through this before ever touching frooteria.de's live DNS.

  • Confirm exactly which record(s) currently make email work (MX → www.frooteria.de → 81.169.202.53), and write the switch plan so it explicitly leaves them untouched
  • Fully build and test the new site on its new host's free subdomain first — never point the real domain at something unverified
  • A day or two before the real cutover, lower frooteria.de's DNS TTL in the GoDaddy dashboard, so the real change propagates fast when it counts
  • On switch day, change only the specific record(s) needed to point the domain at the new host (the A or CNAME for the site) — do not touch nameservers, and do not touch the MX record
  • Immediately after the change, verify both the new website and that email is still arriving
  • Keep the old Strato hosting/account active for a rollback window in case anything breaks
